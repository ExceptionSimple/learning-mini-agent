# ch12 变更说明（对比 ch11）

> 一句话：ch12 的核心变化是引入 **LLM 调用错误修复机制**——把 `agent_loop` 里裸调的流式 LLM 调用包上 `try/except` 与三条恢复路径：**max_tokens 截断**（升级上限 + 续写）、**prompt/上下文超长**（应急压缩）、**429 限流 / 5xx 繁忙**（指数退避 + 备用模型）。
> 恢复原语抽在新增的 `error_recovery.py`，接入点在 `core/agent.py` 的 `agent_loop`；main.py / tool.py / context.py / prompt.py / memory 均不变，ch11 的 Prompt 分段组装、Skills、Memory、Context 压缩照旧。

## 2. 为什么需要错误修复：ch11 的 LLM 调用是"裸调"

ch11 的 `agent_loop` 主循环里，流式 LLM 调用**没有 try/except**，几个真实故障会直接崩掉整轮甚至无限空转：

1. **429 限流 / 503 繁忙**：`core/llm.py` 用 `requests` 直连，非 2xx 时 `response.raise_for_status()` 直接抛异常 → 一路冒泡打断本轮对话，用户重问一次才恢复。
2. **`max_tokens` 截断**：旧代码 `finish_reason` 既不等于 `'stop'` 也不等于 `'tool_calls'` 时 `continue`——输出超长被截断（`finish_reason=="length"`）就落进这个分支，会**用同一批越塞越长的消息无限重发**，既不升上限、也不提示模型续写，是隐性死循环。
3. **上下文超长**：靠模型自己想起调用 `compact` 工具才压缩；模型没调用而历史过长时，API 直接 400 报超长 → 崩。ch09 的 `context.reactive_compact` 应急压缩函数一直存在，但没有触发点。

## 3. 核心变化：三条恢复路径 + 恢复原语模块

### 3.1 对照 DeepSeek 官方错误码（api-docs.deepseek.com/quick_start/error_codes）

| 错误码 | 语义 | ch12 处理 |
|---|---|---|
| 400 格式错误 | message 含 `maximum context length` / `reduce the length` → **上下文超长** | Path 2：`reactive_compact` 一次后重发（只一次） |
| 401 / 402 / 422 | 认证 / 余额不足 / 参数错误 | 非瞬时：不重试，判不可恢复 |
| **429** | 请求速率达上限（TPM/RPM） | Path 3：指数退避 + 抖动重试（≤10 次） |
| **500 / 503** | 服务器故障 / 繁忙 | Path 3：退避 + 连续计数，达阈值切备用模型 |
| 连接类异常 | 不可达 / 超时 | 按 5xx 繁忙路径退避 |

> 注：**DeepSeek 没有 529**（529 是 Anthropic 语义）。初版照抄参考版用了 `consecutive_529`，按官方文档已统一为 5xx / "服务器繁忙"口径。

### 3.2 `error_recovery.py` —— 恢复原语（逐函数都有 docstring 说明作用）

模块只留"错误修复"本身，砍掉了参考脚本里重复的 Anthropic client / tools / prompt / REPL（本项目已分层）：

| 名称 | 作用 |
|---|---|
| `RecoveryState` | 一轮对话内跨多次 LLM 调用的恢复状态：`has_escalated`（是否升过档）、`recovery_count`（续写次数）、`consecutive_overload`（连续繁忙）、`has_attempted_reactive_compact`、`current_model`（可能被切到备用模型） |
| `retry_delay(attempt, retry_after)` | 指数退避 + 抖动（上限 32s）；服务端 `Retry-After` 优先 |
| `classify_transient(e)` | 把异常归类：`ratelimit` / `overloaded` / `None`（非瞬时如 400/401/402/422 返回 None，不盲重试） |
| `_handle_transient(state, category, attempt)` | 公共退避逻辑：更新 `consecutive_overload`，达阈值切 `DEEPSEEK_FALLBACK_MODEL`，返回应睡眠秒数 |
| `with_retry(fn, state)` | **非流式** `invoke()` 的退避重试封装（记忆抽取等旁路调用可用） |
| `stream_with_recovery(llm, state, *, …)` | **流式** `stream()` 的退避重试封装（agent_loop 用）；逐段 `yield ('reasoning'\|'content', delta)`，瞬时错误自动从头重发 |
| `is_prompt_too_long_error(e)` | 按 400 响应体关键字（`maximum context length`、`reduce the length` 等）判上下文超长 |
| `reactive_compact(messages)` | **委托 ch09 `context.reactive_compact`**（真 LLM 摘要 + 保留尾部），不重造轮子 |

```python
# error_recovery.py —— 三条路径的骨架
def stream_with_recovery(llm, state, *, messages, model=None, thinking=True,
                         tools=None, max_tokens=DEFAULT_MAX_TOKENS):
    """流式调用的退避重试：只重试瞬时错误，非瞬时原样上抛交给外层。"""
    if model is None:
        model = PRIMARY_MODEL
    for attempt in range(MAX_RETRIES):
        try:
            for kind, delta in llm.stream(messages=messages, model=model,
                                          thinking=thinking, tools=tools,
                                          max_tokens=max_tokens):
                yield kind, delta
            return
        except Exception as e:
            category = classify_transient(e)     # None=非瞬时
            if category is None:
                raise
            time.sleep(_handle_transient(state, category, attempt))
    raise RuntimeError(f"Max retries ({MAX_RETRIES}) exceeded")
```

模型配置：主模型读 `DEEPSEEK_MODEL`；可选 `DEEPSEEK_FALLBACK_MODEL`（不配则繁忙时保持原模型重试）。打印统一走 `utils.color_print.cprint`（黄=退避，红=降级/放弃）。

### 3.3 `core/agent.py` —— agent_loop 接线

改动集中在一次 LLM 调用点：`self.llm.stream(...)` → `stream_with_recovery(...)` 外包 `try/except`。

```python
# ch12/core/agent.py —— agent_loop（关键片段）
state = RecoveryState()
max_tokens = DEFAULT_MAX_TOKENS                     # 4096
while True:
    try:
        for kind, delta in stream_with_recovery(self.llm, state,
                messages=messages, model=state.current_model,
                thinking=True, tools=self.tools, max_tokens=max_tokens):
            ...  # 打印/累计 reasoning / answer（同 ch11）
    except Exception as e:
        if is_prompt_too_long_error(e) and not state.has_attempted_reactive_compact:
            state.has_attempted_reactive_compact = True
            system_msg = messages[0] if messages[0].get("role") == "system" else None
            rest = messages[1:] if system_msg else messages
            compacted = reactive_compact(rest)      # ch09 应急压缩（LLM 摘要 + 保留尾部）
            messages[:] = ([system_msg] + compacted) if system_msg else compacted
            continue                                # Path 2
        cprint(f"[unrecoverable] {type(e).__name__}: {str(e)[:200]}", color="red")
        messages.append({"role": "assistant", "content": f"[Error] ..."})
        break                                       # 不再让异常崩掉整轮

    if self.llm.finish_reason == "length":          # Path 1
        if not state.has_escalated:
            max_tokens = ESCALATED_MAX_TOKENS       # 8192
            state.has_escalated = True
            continue                                # 丢弃截断输出、重发同请求
        if state.recovery_count < MAX_RECOVERY_RETRIES:   # 3
            state.recovery_count += 1
            messages.append({"role": "assistant", "content": answer_content})  # 截断输出
            messages.append({"role": "user", "content": CONTINUATION_PROMPT})  # 续写提示
            continue
        break
    # 其余同 ch11：append 回答 -> stop 收尾 / tool_calls 执行工具 / compact 工具分支
```

细节：
- **Path 1 的两次形态**：首次 `length` 只升 `max_tokens`（4096→8192）并**丢弃截断输出重发同一请求**（避免把半截话当真喂回历史）；升档后仍截断则**保留截断输出 + 追加 `CONTINUATION_PROMPT`** 让模型接着写（≤3 次）；到上限放弃。这也修掉了旧代码对 `length` 无限 `continue` 的隐性 bug。
- **`model` 从 `state.current_model` 取**：普通请求 = `DEEPSEEK_MODEL`；连续 3 次 5xx 后自动切 `DEEPSEEK_FALLBACK_MODEL`。
- **非瞬时错误记录进消息**：`[Error] {type}: {msg}` 追加成 assistant 消息再结束本轮——用户能在会话里看到失败原因，`after_turn_call` 的记忆抽取也不会因异常被打断。
- 工具循环、`compact` 工具分支、hook 触发（`before_tool_call`）均未动。

## 4. 设计收益

1. **瞬时错误自愈**：429/503/连接抖动走退避自动重试，用户无感知；连续繁忙自动切备用模型，比裸调用稳定得多。
2. **截断可续写、不再死循环**：`length` 从"无限空转"变成"升级→续写→放弃"的收敛路径，长回答体验完整。
3. **触发点补齐**：ch09 一直闲置的 `context.reactive_compact` 应急压缩被真正接到 400 超长错误上（保留 system、只压缩其下历史，一次）。
4. **恢复与主逻辑解耦**：错误分类/退避/降级全在 `error_recovery.py`，`agent_loop` 只多了 try/except 与 finish_reason 分派；`with_retry` 可供 invoke 类旁路调用复用。
5. **非瞬时错误显性化**：4xx（401/402/422）不盲重试、直接记录错误结束，避免无意义烧请求。

---

## 5. 注意点

1. **错误判断依赖 HTTP 状态码**：本项目 LLM 用 `requests` 直连、非 2xx 走 `raise_for_status()`，所以 `classify_transient` 读 `e.response.status_code`。若哪天 LLM 层换成 SDK（OpenAI/Anthropic 官方包），异常形态会变，需同步适配分类函数。
2. **上下文超长靠关键字而非状态码**：DeepSeek 把超长报成普通 400，只能靠 message 文案（`maximum context length` / `reduce the length`）识别——若上游改文案需补关键词。且 reactive_compact 内部要再发一次 LLM 摘要请求，400 那一下已把消息塞得很大，靠 `summarize_history` 里的 80k 字符截断兜底。
3. **流式退避是"整段重试"**：429/5xx 多数在输出首段前就拒绝、无重复；若在输出中途断流，重试会从头重新生成（流式无断点续传），极端场景会看到重复正文——属可接受的取舍，未做半程续传。
4. **备用模型是可选配置**：不设 `DEEPSEEK_FALLBACK_MODEL` 时，繁忙达阈值仅打印提示、保持原模型继续重试，不会崩。
5. **`max_tokens` 数值按模型上限调整**：`DEFAULT_MAX_TOKENS=4096`（对齐项目默认）、`ESCALATED_MAX_TOKENS=8192` 是教学常数；若模型输出上限更高可自行上调，否则升档后 400 会走"不可恢复"结束。
6. **恢复状态按"一轮对话"重置**：`RecoveryState` 在每次 `agent_loop` 入口新建，升级/续写/压缩计数不跨用户问题累计；`consecutive_overload` 亦随新一轮清零。
