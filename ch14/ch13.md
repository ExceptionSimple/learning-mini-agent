> 一句话：ch13 的核心变化是引入 **落盘的任务系统**——新增 `task.py`，把"任务"从 ch06 的内存 todo 升级成 `.tasks/` 下的一文件一任务（`Task` dataclass + `blockedBy` 依赖门禁 + pending→in_progress→completed 状态机），并在 `tool.py` 注册 5 个任务工具（`create_task` / `list_tasks` / `get_task` / `claim_task` / `complete_task`）。

## 2. 为什么需要任务系统：ch06 的 todo 只活在内存里

- **不持久**：ch06 的 `todo_write` 只更新进程内 `CURRENT_TODOS`，agent 一退出就丢，无法跨轮/跨会话回看"做到哪了"。
- **无依赖**：任务之间是平铺的，表达不了"先 A 后 B"的前置关系。
- **与多 agent 脱节**：ch07 引入 subagent 后，父级把大活拆给子代理，但缺一张落盘的"计划看板"让父级记住拆了哪些、完成哪些。

ch13 的 `task.py` 把任务做成**一任务一 JSON 文件**（思路对齐 ch10 `.memory/*.md`、ch04 `.sessions/*.jsonl`），每个任务自带 `status` + `owner` + `blockedBy`，既是记忆也是多 agent 协作的共享黑板。

## 3. 核心变化：`task.py`（任务模型与门禁）+ `tool.py`（接线）

### 3.1 `task.py` —— Task 数据模型 + `.tasks/` 落盘

```python
WORKDIR = Path.cwd()
TASKS_DIR = WORKDIR / ".tasks"
TASKS_DIR.mkdir(exist_ok=True)          # 导入即建目录，避免首次写盘报错

@dataclass
class Task:
    """一条任务。status 流转：pending -> in_progress -> completed。"""
    id: str
    subject: str
    description: str
    status: str          # pending | in_progress | completed
    owner: str | None    # Agent name (multi-agent scenarios)
    blockedBy: list[str] # Dependency task IDs（都 completed 才允许 claim）

def _task_path(task_id: str) -> Path:
    return TASKS_DIR / f"{task_id}.json"

def create_task(subject: str, description: str = "",
                blockedBy: list[str] | None = None) -> Task:
    task = Task(
        id=f"task_{int(time.time())}_{random.randint(0, 9999):04d}",  # 时间戳+随机数保证唯一
        subject=subject, description=description,
        status="pending", owner=None, blockedBy=blockedBy or [],
    )
    save_task(task)      # asdict → json.dumps(indent=2) 写盘
    return task
```

- **持久化**：`save_task/load_task` 一个函数一行，`asdict` 序列化、`Task(**json)` 还原；`list_tasks` 用 `glob("task_*.json")` 限定 + 文件名排序，保证概览顺序稳定、过滤杂散文件。
- **依赖门禁**：`can_start(task_id)` 检查 `blockedBy` 是否全部 `completed`；**缺失的依赖按"阻塞"处理**——任务 B 引用了不存在的 A，宁可停在 pending 等人修，也不允许跳依赖提前开跑。

### 3.2 认领 / 完成状态机（返回值给模型，彩色日志给人）

```python
def claim_task(task_id: str, owner: str = "agent") -> str:
    """认领任务（多 agent 场景表示"我要干这个"）。
    门禁：仅 pending 且所有依赖 completed 才能认领；成功则置 owner + in_progress。"""
    task = load_task(task_id)
    if task.status != "pending":
        return f"Task {task_id} is {task.status}, cannot claim"
    if not can_start(task_id):
        deps = [d for d in task.blockedBy
                if not _task_path(d).exists() or load_task(d).status != "completed"]
        return f"Blocked by: {deps}"
    task.owner = owner
    task.status = "in_progress"
    save_task(task)
    cprint(f"[claim] {task.subject} → in_progress (owner: {owner})", color="cyan")
    return f"Claimed {task.id} ({task.subject})"

def complete_task(task_id: str) -> str:
    """完成任务，并报告因此解锁的下游任务。"""
    task = load_task(task_id)
    if task.status != "in_progress":
        return f"Task {task_id} is {task.status}, cannot complete"
    task.status = "completed"
    save_task(task)
    unblocked = [t.subject for t in list_tasks()
                 if t.status == "pending" and t.blockedBy and can_start(t.id)]
    cprint(f"[complete] {task.subject} ✓", color="green")
    msg = f"Completed {task.id} ({task.subject})"
    if unblocked:
        msg += f"\nUnblocked: {', '.join(unblocked)}"     # 解锁的下游喂回给 LLM
        cprint(f"[unblocked] {', '.join(unblocked)}", color="yellow")
    return msg
```

**为什么 `complete_task` 返回 `Unblocked: ...`**：依赖解锁是"完成"的连带价值，直接拼进返回值让模型知道"接下来可以认领谁"，把下一步行动决策交给模型而不是靠人看日志。

**约定**（对齐 memory / error_recovery）：`cprint` 彩色日志给人看；`return` 的纯字符串才是模型收到的 tool result。颜色：[create] 蓝、[claim] 青、[complete] 绿、[unblocked] 黄。

### 3.3 `tool.py` —— 5 个任务工具，8 → 13，agent_loop 零改动

5 个任务工具以 `StructuredTool` 追加在 `TOOL_DEFINITIONS` 列表**末尾**（`compact` 也在列表中——它靠名字被 `agent_loop` 特判拦截，与排第几位无关）：

```python
from task import (
    run_create_task, run_list_tasks, run_get_task,
    run_claim_task, run_complete_task,
)

# 关键：name / description / parameters 就是模型唯一能看到的工具说明——
# 精简、准确即可，属性级不必再写 description（对齐 OpenAI 工具格式）。
StructuredTool(name="create_task", description="Create a new task with optional blockedBy dependencies.",
    args_schema={"type": "object",
                 "properties": {"subject":     {"type": "string"},
                                "description": {"type": "string"},
                                "blockedBy":   {"type": "array", "items": {"type": "string"}}},
                 "required": ["subject"]},
    func=run_create_task),
StructuredTool(name="list_tasks", description="List all tasks with status, owner, and dependencies.",
    args_schema={"type": "object", "properties": {}, "required": []},
    func=run_list_tasks),
# get_task / claim_task / complete_task 同构：task_id 必填
#   "Get full details of a specific task by ID."
#   "Claim a pending task. Sets owner, changes status to in_progress."
#   "Complete an in-progress task. Reports unblocked downstream tasks."
```

- **工具名与函数 kwarg 逐一对齐**：`create_task` 的 schema property 是 `subject`/`description`/`blockedBy`，`claim_task`/`get_task`/`complete_task` 是 `task_id` —— `handler(**tool.tool_input)` 才能展开成功。
- **为什么不用改 `agent_loop`**：`core/agent.py` 只把 `compact` 特殊分支；其余工具一律 `TOOL_CALL_MAP[tool.name]` → `handler(**tool_input)` → 结果 append 成 `role="tool"` 消息。任务工具走的就是这条通用路径。
- **为什么不用改 `prompt.py`**：ch11 的 `tools` 段由 `TOOLS` schema 运行时推导（`enabled_tools`），5 个新工具的 description/schema 自动进入 system prompt，模型天生"知道"自己有这些工具。
- 注册顺序即 `TOOLS` 顺序：任务工具排在同为工具的 `task`（委派）、`load_skill`（技能）之后、位于列表末尾；`compact` 虽非末位，但 `agent_loop` 按名字特判，位置无关。

## 4. 设计收益

1. **落盘即持久**：`.tasks/task_*.json` 一任务一文件，agent 退出/重启不丢，可跨会话回看进度（对齐 `.memory/`、`.sessions/` 的思路）。
2. **依赖门禁防乱序**：`blockedBy` 显式表达前置关系，`can_start` 对缺失依赖按阻塞处理——规划有洞时任务卡住等人修，而不是静默跳过依赖提前开跑。
3. **零改造接入工具体系**：走 `TOOL_CALL_MAP` 通用分发 + ch11 的运行时工具推导，`agent.py` / `prompt.py` / `error_recovery.py` 一行没动，纯"加文件 + 加工具实例"就接进主循环。
4. **返回值回喂 LLM**：给人看的彩色日志与给模型看的字符串分离；`complete_task` 把"解锁了谁"拼进返回值，让模型自己决定下一步认领哪个任务。
5. **多 agent 预留**：`owner` 字段 + `claim_task(owner=...)` 参数已为并行/多身份场景留位；同时 subagent 的 `SUB_TOOLS` 仍只有 bash/read/write/edit/glob 五个文件工具——任务工具**不泄漏给子代理**，拆解与认领的决策权收敛在主对话。

## 5. 注意点

1. **两个"task"别混淆**：ch07 的工具叫 `task`（`func=spawn_subagent`，委派子代理）；ch13 的是 `create_task`/`claim_task` 等（持久任务看板）。同名概念不同层，看 schema/description 区分。
2. **一次一任务 vs 先规划后执行**：当前形态是模型"建一个 → 认领一个 → 完成一个"地推进；README 里的后期测试正是想改成**开场一次 `create_task` 建好 N 个任务，再逐个 claim/complete**——需要 agent 在首轮连续发起多次工具调用（或用 ch14 的前置规划），现版本未强制。
3. **状态机严格 + 错误兜底**：`claim` 仅 `pending`、`complete` 仅 `in_progress`，非法状态返回说明字符串不抛异常；`run_get_task`/`run_claim_task`/`run_complete_task` 对 `FileNotFoundError`（模型传错/截断的 id）返回友好提示，不让 agent 崩掉。
4. **清场靠删目录**：`.tasks/*.json` 会随使用积累；`list_tasks` 只认 `task_*.json` 且排序稳定。想重置进度直接清空 `.tasks/`（已进 `.gitignore`，不会误提交）。
5. **依赖环未做检测**：两个任务互相 `blockedBy` 会双双永久阻塞（`can_start` 都 False）。教学版本未做环检测，靠模型规划自觉避免。
6. **工作副本差异提醒**：当前 ch13 目录里的 `core/agent.py` 比 ch12 多一行——append assistant 消息时写入 `"reasoning_content": reasoning_content`（116-118 行）。这属于运行调试期加的"历史保留思考链"字段，**与任务机制无关**；若想得到与 ch12 纯净对比，可忽略或回滚该行。
