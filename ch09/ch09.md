## 2. 核心变化：Context 上下文压缩

### 2.1 背景

会话越长，`messages` 里积累的历史（用户问答、工具调用与结果）越多，上下文占用越大，最终逼近模型 token 上限。ch09 的思路是：**把早前对话压缩成一段 LLM 摘要**，模型只保留摘要 + 系统提示，从而给长会话"续命"。

### 2.2 入口：`compact` 工具

`tool.py` 在 ch08 的 7 个工具基础上，追加 `compact` 工具：

```python
# ch09/tool.py
StructuredTool(
    name="compact",
    description="Summarize earlier conversation to free context space.",
    args_schema={"type": "object", "properties": {"focus": {"type": "string"}}},
    func=None,          # ★ 无对应 handler，agent.py 里对 compact 做特殊分支处理
)
```

`func=None` 是刻意的：压缩不是"执行一个普通函数"，而是要**就地改写 `messages` 本身**，普通工具执行模型拿不到 `messages` 引用，所以 `compact` 在 `agent.py` 的循环里被特判。

### 2.3 接线：`core/agent.py` 的 compact 特殊分支

```python
# ch09/core/agent.py —— 工具执行循环内
print(f"\033[33m[tool] {tool.name}\033[0m")

if tool.name == "compact":
    system_msg = messages[0]
    compact_history_msg = compact_history(messages[1:])     # 摘要 system 之后的所有消息
    messages[:] = [system_msg] + compact_history_msg        # 原地替换：system + 摘要
    break

handler = TOOL_CALL_MAP[tool.name]
result = handler(**tool.tool_input)
tool_call_context.tool_result = result
messages.append({"role": "tool", "tool_call_id": tool.tool_id, "content": result})
```

语义：当模型判断上下文过长、调用 `compact` 时——
1. 保留 `messages[0]`（system 提示词，含角色设定 + skills 清单）；
2. 把 `messages[1:]`（此前的用户提问 / 助手回答 / 工具往返，含当前这一轮）整体交给 `compact_history()` 摘要；
3. `messages[:] = [system_msg] + [摘要]` 原地替换，`break` 跳出工具循环；
4. 回到 `while True` 顶部，用压缩后的上下文继续下一轮流式对话。

### 2.4 `context.py` 的结构：四层压缩 + 应急

`context.py` 按注释规划了 L1~L4 四层递进的压缩手段 + 一个兜底应急函数：

| 层 | 函数 | 手段 | 接线状态 |
|---|---|---|---|
| L1 | `snip_compact(messages, max_messages=50)` | 保头 3 条 + 保尾，中间裁剪成 `[snipped N messages]`；会前后补足 tool-call/result 对，保证消息完整 | ⚠️ 定义了未接线 |
| L2 | `collect_tool_results` + `micro_compact` | 只保留最近 `KEEP_RECENT=3` 条工具结果，更早且 >120 字符的结果替换为占位符 | ⚠️ 定义了未接线 |
| L3 | `persist_large_output` + `tool_result_budget` | 工具结果超阈值就落盘 `tool_results/{tool_call_id}.txt`，上下文只留前 2000 字符预览；总预算超 200k 时从最大结果开始裁 | ⚠️ 定义了未接线 |
| **L4** | `write_transcript` + `summarize_history` + **`compact_history`** | **LLM 全量摘要**：先落盘 transcript，再让 LLM 把整段对话压成一段摘要 | ✅ **唯一接线**（`compact` 工具触发） |
| 兜底 | `reactive_compact(messages)` | 应急：API 报"prompt too long"时，落盘 + 摘要 + 只保留末尾 5 条 | ⚠️ 定义了未接线 |

**L4 的完整调用链（ch09 实际生效路径）**：

```python
# ch09/context.py
def compact_history(messages):
    transcript_path = write_transcript(messages)        # ① 把原消息逐行写入 transcript/transcript_{ts}.jsonl
    print(f"[transcript saved: {transcript_path}]")
    summary = summarize_history(messages)               # ② LLM 摘要
    return [{"role": "user", "content": f"[Compacted]\n\n{summary}"}]

def write_transcript(messages):
    TRANSCRIPT_DIR.mkdir(parents=True, exist_ok=True)
    path = TRANSCRIPT_DIR / f"transcript_{int(time.time())}.jsonl"
    with path.open("w") as f:
        for msg in messages:
            f.write(json.dumps(msg, default=str) + "\n")
    return path

def summarize_history(messages: list):
    conversation = json.dumps(messages, default=str)
    MAX = 80000                                     # 过长先保头尾裁中间，再交给 LLM
    if len(conversation) > MAX:
        head, tail = MAX // 2, MAX // 2
        conversation = conversation[:head] + "\n...[middle truncated]...\n" + conversation[-tail:]
    prompt = ("Summarize this coding-agent conversation so work can continue.\n"
              "Preserve: 1. current goal, 2. key findings/decisions, 3. files read/changed, "
              "4. remaining work, 5. user constraints.\nBe compact but concrete.\n\n" + conversation)
    llm = DeepSeekLLM(api_key=..., base_url=...)
    response = llm.invoke(messages=[{"role": "system", "content": prompt}], model=...)
    return response['content']
```

摘要通过**单条 system 消息**把指令 + 待摘要全文一并交给 `DeepSeekLLM.invoke()`（非流式，复用 ch07 重构的通道），返回的 `content` 就是压缩后的摘要。

### 2.5 压缩的"证据保全"：transcript 落盘

每次 `compact_history` 触发，都会先把**压缩前的完整消息**逐行写入 `transcript/transcript_{时间戳}.jsonl`，再动手压缩。这样即便摘要丢细节，原始对话仍可追溯。运行几次后 `transcript/` 会累积多个文件（当前 ch09 下已有多个 `transcript_*.jsonl`）。

## 4. 设计收益

1. **长会话续命**：把"整段历史"降维成"一段摘要"，上下文占用从随对话线性增长变为近恒定。
2. **模型驱动、按需触发**：压缩不依赖固定阈值，由模型感知上下文紧张时主动 `compact`（工具 description 即提示）。
3. **压缩留痕**：transcript 落盘让"摘要丢了什么"可追溯，比纯内存丢弃更安全。
4. **四层递进设计**：L1~L3 提供从轻到重的非 LLM 压缩手段（裁 / 占位 / 落盘预览），可作为后续自动触发的备选，不必每次压缩都花一次 LLM 调用。
5. **复用既有通道**：摘要走 ch07 重构好的 `invoke()` 非流式通道，无新增机制。

---

## 5. 注意点

1. **当前只有 L4 接线**：`snip_compact` / `micro_compact` / `persist_large_output`+`tool_result_budget` / `reactive_compact` 以及常量 `CONTEXT_LIMIT`/`KEEP_RECENT`/`PERSIST_THRESHOLD`/`TOOL_RESULT_DIR` 均已定义但**从未被调用**（`TOOL_RESULT_DIR` 因此也不会生成 `tool_results/`）。它们目前是"预留资产"而非生效逻辑——若要按 L1~L3 落地，需要另行接线触发点。
2. **压缩完全靠模型自觉**：没有"消息超阈值自动压缩"的代码，也没有系统提示词指导模型"何时该 compact"，只凭工具 description。模型若不调用 `compact`，压缩永不发生。
3. **compact 会丢"当前轮上下文"**：`compact_history(messages[1:])` 连最新用户提问 + 本次 assistant 的 compact 请求一起摘要掉，压缩后只剩 `[system, {摘要}]`。若希望压缩后仍带着用户最近提问继续，需要调整该分支保留 `messages[-1]`（曾有此写法，后简化去掉）。
4. **摘要用单条 system 消息承载全文**：`summarize_history` 里 `messages=[{"role":"system","content":prompt}]` 无 user 消息，语义上"指令+内容"同置 system，某些 API 可能拒绝纯 system-only 请求。
5. **`compact` 的 `func=None` 由 agent.py 特判兜底**：若未来重构工具循环，需同步保留该特殊分支，否则 `TOOL_CALL_MAP['compact']` 取到 `None` 会直接执行失败。
6. **摘要截断阈值与提示词硬编码在函数内**：`MAX = 80000`、摘要要求清单（goal/findings/files/remaining/constraints）都写死在 `summarize_history`，复用或调整需改源码。
