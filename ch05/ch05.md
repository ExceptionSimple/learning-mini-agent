# ch05 架构升级说明（对比 ch04）

> 一句话：ch05 把 ch04 的"脚本式"实现升级为 **分层 + 类型化对象 + 依赖注入** 的实现。
> 核心变化是两条：工具从"裸 dict"变为"对象 + 序列化"；`tool_calls` 从"裸 dict"变为"类型化对象"。

---

## 1. 目录结构对比

```text
ch04（扁平，工具与定义混在一个文件）          ch05（分层，按职责拆包）
├── main.py                                   ├── main.py              # 入口：组装 chat + Agent，注入 tools
├── tools.py          # 工具函数 + 手写dict    ├── core/                # 核心编排层（新增包）
│                      + TOOL_CALL_MAP 混装    │   ├── agent.py         #   Agent 类：持 llm + tools
├── permission.py     # 消费裸 dict            │   ├── llm.py           #   DeepSeekLLM：返回 ToolCall 对象
├── session_manage.py # jsonl 会话             │   ├── types.py         #   LLMMessage TypedDict
└── llm/                                      │   └── __init__.py
    └── chat_model.py # DeepSeekChat          ├── tool.py             # 工具定义：用 StructuredTool 组装
                                              ├── tools/              # 工具实现包（新增）
                                              │   ├── structed_tool.py #   StructuredTool / ToolCall / 序列化
                                              │   ├── base_tools.py    #   纯执行函数（run_bash...）
                                              │   └── __init__.py
                                              ├── permission.py       # 消费 ToolCall 对象
                                              └── session_manage.py   # jsonl 会话（与 ch04 一致）
```

## 2. 五大核心变化

### 2.1 工具定义：裸 dict → `StructuredTool` 对象 + 序列化

ch04 中 `TOOLS` 是手写 dict，schema 硬编码在 `tools.py` 末尾：

```python
# ch04/tools.py —— 裸 dict
TOOLS = [
    {"type": "function", "function": {
        "name": "bash", "description": "Run a shell command.",
        "parameters": {
            "type": "object",
            "properties": {"command": {"type": "string", "description": "..."}},
            "required": ["command"]}}},
    ...
]
TOOL_CALL_MAP = {"bash": run_bash, "read_file": run_read, ...}
```

ch05 用 `StructuredTool` 对象描述工具，`tool_to_openai()` 统一序列化成 API 格式，新增工具只需新增一个实例：

```python
# ch05/tool.py —— 对象 + 序列化
TOOL_DEFINITIONS = [
    StructuredTool(
        name="bash",
        description="Run a shell command.",
        args_schema={
            "type": "object",
            "properties": {"command": {"type": "string", "description": "..."}},
            "required": ["command"],
        },
        func=run_bash,
    ),
    ...
]
TOOLS = [tool_to_openai(t) for t in TOOL_DEFINITIONS]     # 序列化到 API 格式
TOOL_CALL_MAP = {t.name: t.func for t in TOOL_DEFINITIONS}
```

同时把"工具实现"（`run_bash` 等执行函数）拆到 `tools/base_tools.py`，"工具定义"（`tool.py`）与"序列化/数据结构"（`tools/structed_tool.py`）分离。

### 2.2 `tool_calls`：裸 dict → `ToolCall` 类型化对象

ch04 全程裸 dict 访问，在 main.py 和 permission.py 里各 `json.loads` 解析一次：

```python
# ch04 —— 裸 dict
tool['function']['name']                     # 拿名字
json.loads(tool['function']['arguments'])    # 手动解析参数
tool['id']                                   # 拿 id
```

ch05 由 LLM 客户端解析一次成 `ToolCall` 对象（`tool_id` / `name` / `tool_input`），消费方直接用属性：

```python
# ch05 —— 类型化对象
tool.name                    # 拿名字
handler(**tool.tool_input)   # 参数已是 dict，直接解包执行
tool.tool_id                 # 拿 id
tool.to_openai()             # 回传给 API 时再序列化
```

**序列化职责收敛到一处**：`ToolCall.to_openai()` 负责把对象还原成 OpenAI 格式。这里有个关键约束——API 要求 `function.arguments` 必须是 **JSON 字符串**，因此 `to_openai()` 内必须 `json.dumps(self.tool_input)`，而执行工具时才 `json.loads`（ch04 时代的"裸 dict 满天飞 + 到处解析"在这个坑上更容易出错）。

### 2.3 Agent：模块级函数 → `Agent` 类 + 依赖注入

ch04 的 `agent_loop` 是自由函数，`chat` 是 main.py 里的全局单例：

```python
# ch04/main.py
chat = DeepSeekChat(...)          # 全局单例
def agent_loop(messages: list):   # 自由函数，只能操作全局 chat
    ...
```

ch05 把编排逻辑收进 `Agent` 类，`llm` 和 `tools` 通过构造函数注入：

```python
# ch05/core/agent.py
class Agent:
    def __init__(self, llm: DeepSeekLLM, tools: list[StructuredTool]):
        self.llm = llm
        self.tools = tools

    def agent_loop(self, messages: list):
        ...  # 方法体，使用 self.llm / self.tools
```

```python
# ch05/main.py —— 组装注入
chat = DeepSeekLLM(...)
agent = Agent(llm=chat, tools=TOOLS)
agent.agent_loop(messages=messages)
```

Agent 不再依赖具体 LLM/工具实现，可以复用、单测，也支持未来创建多个不同配置的 Agent 实例。

### 2.4 LLM 客户端：`DeepSeekChat` → `DeepSeekLLM`，返回类型化结果

- 位置：`llm/chat_model.py` → `core/llm.py`，对齐到 core 编排层。
- 命名：`DeepSeekChat` → `DeepSeekLLM`（职责更贴近"LLM 接入"，而非"对话"）。
- 输出：`stream()` 结束块把累计的 OpenAI `tool_calls` 统一解析成 `list[ToolCall]`，`self.tool_calls` 声明为 `list[ToolCall]`。

### 2.5 类型约束：新增 `core/types.py`

用 `TypedDict` 定义 `LLMMessage`（role / content / tool_call_id / tool_calls 等字段），为消息结构提供静态约束，ch04 没有任何类型层。

## 3. 其它改进点

| 项 | ch04 | ch05 |
|---|---|---|
| 模型名 | `main.py` 硬编码 `"deepseek-v4-pro"` | `os.environ.get("DEEPSEEK_MODEL")` |
| session_id | 遗留调试值 `"e2c24ac0" or uuid4()` | 直接 `uuid.uuid4().hex[:8]` |
| 权限层输入 | `check_permission(tool)` 消费裸 dict | `check_permission(tool: ToolCall)` 消费对象（`tool.name` / `tool.tool_input`） |

---

## 4. 设计收益

1. **职责边界清晰**：编排（core/）、工具实现（tools/base_tools.py）、工具定义（tool.py）、权限（permission.py）各司其职。
2. **新增工具成本低**：只需在 `TOOL_DEFINITIONS` 里加一个 `StructuredTool` 实例 + 一个 `run_*` 函数，不再手写 dict。
3. **序列化/解析收敛**：`ToolCall` 集中处理"API 字符串 ↔ 执行 dict"的转换，杜绝散落的 `json.loads`。
4. **可测试、可组合**：`Agent(llm, tools)` 依赖注入，可用 mock LLM 做单测；可同时跑多个 Agent。

---

## 5. 代价与注意点（踩过的坑）

1. **导入边界**：`core` 是包（有 `__init__.py`），`ch05` 本身不是包。`core/` 内部同包模块要用相对导入（`from .llm import DeepSeekLLM`）；跨到 `ch05` 根下的模块（`tool.py`、`tools/`）用绝对导入（`from tool import TOOLS`）。不要用 `from ..tool import ...`——`ch05` 非包，`..` 会越过顶层包报错。运行方式依赖 `python3 main.py`（`ch05` 在 `sys.path[0]`）。
2. **`arguments` 必须是字符串**：API 往返时 `function.arguments` 恒为 JSON 字符串（`ToolCall.to_openai()` 里 `json.dumps`）；只在执行工具那一刻才 `json.loads`（`handler(**tool.tool_input)`）。
3. **`core/types.py` 命名风险**：文件叫 `types.py` 与标准库 `types` 同名，若 `core/` 目录被塞进 `sys.path` 会遮蔽标准库。目前作为包导入无碍，但不要对 `core/` 做 `sys.path.insert`。
