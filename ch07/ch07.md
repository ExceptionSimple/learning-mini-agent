# ch07 变更说明（对比 ch06）

> 一句话：ch07 的核心变化是引入 **Subagent（子代理）**，把复杂子任务通过一个 `task` 工具委派给**上下文隔离**的子代理执行，子代理完成后只返回最终结论。
> ch06 的 Hook 事件系统与分层架构不变，ch07 在其上新增了"任务委派"能力，并为支撑子代理把 LLM 的非流式通道 `invoke()` 做了重构。

## 2. 核心变化：Subagent 子代理

### 2.1 什么是 subagent

ch06 的 Agent 是"单 Agent + 多工具"：所有工具调用都在同一个 `messages` 上下文里串行执行。ch07 新增一种"委派"能力——父 Agent 遇到复杂子任务时，不自己逐步完成，而是调用一个名为 `task` 的工具，把任务交给一个**全新上下文、独立工具集**的子代理去跑，子代理跑完只回传一句最终结论。

子代理有两点关键设计：

1. **上下文隔离**：子代理启动时用 `SUB_SYSTEM` + 任务描述新建 `messages`，与父 Agent 的历史消息完全隔离，互不污染。
2. **工具集隔离 + 禁止再委派**：子代理只暴露文件/命令类基础工具，**不包含 `task` 工具**，且系统提示词明确 `Do not delegate further.`，从机制和指令两个层面切断无限套娃。

### 2.2 入口：`task` 工具

ch07 的 `tool.py` 在原有 5 个工具基础上，追加一个 `task` 工具：

```python
# ch07/tool.py —— 新增 task 工具，func 直接指向 spawn_subagent
StructuredTool(
    name="task",
    description="Launch a subagent to handle a complex subtask. Returns only the final conclusion.",
    args_schema={
        "type": "object",
        "properties": {"description": {"type": "string"}},
        "required": ["description"],
    },
    func=spawn_subagent,
)
```

`TOOL_DEFINITIONS` 现在有 6 个工具，`task` 复用既有的 `StructuredTool` / `tool_to_openai` 序列化，无需任何新机制。

### 2.3 `subagent.py` 内部结构

`subagent.py` 新增三个部件：

- **`SUB_TOOL_DEFINITIONS`**：子代理专属工具集，只有 `bash` / `read_file` / `write_file` / `edit_file` / `glob` 五个（与父 Agent 同源函数，但**刻意不含 `task`**）。
- **`SUB_SYSTEM`**：子代理系统提示词——`"You are a coding agent at {WORKDIR}. Complete the task you were given, then return a concise summary. Do not delegate further."`
- **`spawn_subagent(description)`**：子代理主循环，核心逻辑如下。

```python
# ch07/subagent.py —— 子代理主循环（简化）
messages = [
    {"role": "system", "content": SUB_SYSTEM},
    {"role": "user", "content": description},      # 全新上下文，与父隔离
]
llm = DeepSeekLLM(...)

for _ in range(30):                                # 最多 30 轮，防死循环
    response = llm.invoke(                         # ★ 用 invoke 非流式，而非父 Agent 的 stream
        messages=messages,
        model=os.environ.get("DEEPSEEK_MODEL"),
        tools=SUB_TOOLS,
    )

    if response['finish_reason'] == "stop":        # 模型给出最终答案
        result = extract_text(response['content'])
        break

    if response['finish_reason'] != "tool_calls":
        continue

    tool_calls = llm.tool_calls                    # invoke 已解析为 ToolCall 对象
    messages.append({
        "role": "assistant", "content": None,
        "tool_calls": [tc.to_openai() for tc in tool_calls],
    })
    for tool in tool_calls:
        # 复用 ch06 的 before_tool_call 权限 hook
        ctx = ToolCallHookContext(tool_name=tool.name, tool_input=tool.tool_input,
                                  tool_result='', messages=messages, tool=tool)
        if not trigger_hook("before_tool_call", ctx):
            continue
        result = SUB_TOOL_CALL_MAP[tool.name](**tool.tool_input)
        messages.append({"role": "tool", "tool_call_id": tool.tool_id, "content": result})

if not result:
    result = "Subagent stopped after 30 turns without final answer."

print(f"\033[35m[Subagent done]\033[0m")
return result                                          # 只回传最终结论
```

**与父 Agent（`core/agent.py`）的对照**：

| 维度 | 父 Agent（`Agent.agent_loop`） | 子代理（`spawn_subagent`） |
|---|---|---|
| 调用方式 | `llm.stream()` 流式，逐段打印思考/回答 | `llm.invoke()` 非流式，整段取回 |
| 上下文 | 复用 `main.py` 传入的 `messages` | 自己新建，与父隔离 |
| 工具集 | `TOOLS`（6 个，含 `task`） | `SUB_TOOLS`（5 个，无 `task`） |
| 结束条件 | `while True` + `finish_reason == 'stop'` | `for _ in range(30)` + `finish_reason == 'stop'` |
| 产物 | 边想边答，直接输出给用户 | 只返回一句最终结论给父 Agent |

## 3. 支撑变化：`core/llm.py` 的 `invoke()` 重构

ch06 的 `invoke()` 是早期遗留的雏形：`tool_calls` 原样透传 API 原始 dict，`model` 还硬编码默认 `"deepseek-chat"`，且无错误处理。ch07 要支撑子代理的非流式循环，对其做了三处改动：

### 3.1 抽取 `_parse_tool_calls`，消除重复

`invoke()` 与 `stream()` 原来各自把 `raw_tool_calls` 解析成 `ToolCall` 对象（`stream` 在 `finally` 里做，`invoke` 干脆没做）。ch07 抽出公共方法：

```python
# ch07/core/llm.py —— 新增公共解析
def _parse_tool_calls(self, raw_tool_calls: list | None) -> list[ToolCall]:
    parsed = []
    for tool_call in raw_tool_calls or []:
        parsed.append(ToolCall(
            tool_id=tool_call['id'],
            name=tool_call['function']['name'],
            tool_input=json.loads(tool_call['function']['arguments']),
        ))
    return parsed
```

### 3.2 `invoke()` 与 `stream()` 输出槽位对齐

`invoke()` 现在同样把结果解析为 `ToolCall` 对象存入实例，与 `stream()` 行为一致：

```python
# ch07/core/llm.py —— invoke 内
self.finish_reason = finish_reason
self.tool_calls = self._parse_tool_calls(message.get('tool_calls'))

return {
    'id': data['id'],
    'role': message['role'],
    'content': message['content'],
    'reasoning_content': message.get('reasoning_content'),
    'tool_calls': self.tool_calls,          # ★ 从原始 dict 变为 ToolCall 对象列表
    'finish_reason': finish_reason,
}
```

调用方（子代理）于是能直接 `llm.tool_calls` 拿到 `ToolCall`，再 `tc.to_openai()` 回传。

### 3.3 其它微调

- **`model` 默认值**：`"deepseek-chat"` → `None`，模型统一由调用方显式传入（父/子都传 `os.environ.get("DEEPSEEK_MODEL")`）。
- **400 错误诊断**：`invoke()` 与 `stream()` 都在 `raise_for_status()` 之前，对 `status_code == 400` 的响应打印 `message` / `type` / `param` / `code` 四段红色信息，方便排障（打印后仍会抛出异常）。

## 4. 设计收益

1. **任务委派**：父 Agent 把复杂子任务外包给子代理，主上下文只保留"委派"这一条消息，避免长任务把主上下文越滚越长。
2. **上下文隔离**：子代理的 `messages` 完全独立，父 Agent 只关心"结论是什么"，不关心"过程有多乱"。
3. **防无限委派**：`SUB_TOOLS` 不含 `task` + `SUB_SYSTEM` 显式 `Do not delegate further.`，双层保险，子代理无法再开子代理。
4. **复用既有积木**：子代理零新增机制地复用了 `StructuredTool`、`ToolCall.to_openai()`、`before_tool_call` 权限 hook，以及本次重构的 `invoke()` 非流式通道。
5. **流式/非流式分工明确**：父 Agent 面向人，用 `stream()` 边想边打；子代理面向父 Agent，用 `invoke()` 静默算完只回结论。

## 5. 注意点

1. **`from pydantic import tools` 是未使用导入**：`ch07/core/llm.py` 第 2 行引入了 `pydantic.tools`，但全文件未用到，属于遗留死代码（未删除，仅提示）。
2. **子代理有 30 轮硬上限**：超时返回固定文案 `"Subagent stopped after 30 turns without final answer."`，父 Agent 会把它当普通工具结果收下，需注意结论质量可能因截断而下降。
3. **`invoke()` 返回的 `tool_calls` 语义变化**：从"API 原始 dict"变成"`ToolCall` 对象列表"。任何依赖旧 `invoke()` 返回结构的调用方都要同步改（当前仅 `subagent.py` 使用，已适配）。
4. **子代理工具集刻意缺 `task`**：这是防套娃的关键设计，若未来要给子代理加新工具，不要顺手把 `task` 加进去，除非明确想允许"多级委派"。
5. **`before_tool_call` 权限 hook 被子代理复用**：子代理执行工具同样会过 `check_permission`，被拒绝时追加 `Permission denied.` 并跳过——权限管控对子代理同样生效。
