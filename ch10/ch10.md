## 2. 核心变化：Memory 记忆系统

### 2.1 记忆是什么、存在哪

一条记忆 = `.memory/` 下一个 `<slug>.md` 文件，头部 frontmatter 用本项目约定格式，正文是 markdown：

```markdown
---
name: user-name
description: 用户叫小明
metadata:
  type: user          # 记忆类型 ∈ {user, feedback, project, reference}
---

用户偏好称呼：小明。
```

配套的 `.memory/MEMORY.md` 是自动重建的索引，供 SYSTEM 目录与检索用：

```text
- [project-stack](project-stack.md) — 技术栈为 Python
- [user-name](user-name.md) — 用户叫小明
```

`MEMORY_TYPES = ["user", "feedback", "project", "reference"]`：user=用户偏好、feedback=指导意见、project=项目事实、reference=外部资料指针（与抽取 prompt 的映射一致）。

### 2.2 记忆的读写 API（`memory.py` 纯函数层）

| 函数 | 作用 |
|---|---|
| `write_memory_file(name, mem_type, description, body)` | 按 name 生成 slug 写 `.md`，并重建索引 |
| `_parse_frontmatter(text)` / `_rebuild_index()` | 解析嵌套 frontmatter / 重建 `MEMORY.md` |
| `read_memory_index()` | 读索引（供 system prompt） |
| `read_memory_file(filename)` / `list_memory_files()` | 读单条 / 列出全部（含 name/desc/type/body） |
| `select_relevant_memories(messages, max_items=5)` | 挑出与近期对话相关的记忆：**优先 LLM 选择，失败退化为关键词匹配** |
| `load_memories(messages)` | 把选中记忆拼成 `<relevant_memories>…</relevant_memories>` 包裹文本（供注入） |
| `extract_memories(messages)` | 从最近 10 条消息里抽新记忆并落盘（LLM 返回空/失败则静默） |
| `consolidate_memories()` | ≥ `CONSOLIDATE_THRESHOLD`(10) 条时 LLM 合并去重/清过期；空结果保护不清库 |
| `build_memory_system_prompt()` | 生成"记忆可用目录 + 行为引导"的 SYSTEM 片段 |

### 2.3 记忆的生命周期（Hook 接线）

记忆不再是"调一次工具"，而是围绕每一轮对话**自动旁路**：注入 → 对话 → 抽取。全部通过 hook 事件：

```python
# ch10/main.py —— 注入：每轮对话前（before_turn_call）
def before_turn_call(context: LLMCallHookContext):
    cprint("[HOOK] before_turn_call: 注入相关记忆", color="bright_magenta")
    msg = context.messages
    if not msg:
        return True
    block = load_memories(msg)                       # 无记忆文件时返回 ""
    if block and msg[-1].get("role") == "user":
        msg[-1]["content"] = f"{msg[-1].get('content', '')}\n\n{block}"   # 相关记忆拼到本轮问题后面
    return True

register_hook("before_turn_call", before_turn_call)

# ch10/main.py —— 抽取：每轮对话后（after_turn_call 复挂第二个回调）
def after_turn_memory(context: LLMCallHookContext):
    cprint("[HOOK] after_turn_call: 抽取记忆", color="bright_magenta")
    extract_memories(context.messages)               # LLM 失败时静默，不阻塞主流程
    return True

register_hook("after_turn_call", after_turn_memory)
```

主循环随之调整（context 提前构造，供两个前后事件共用）：

```python
while True:
    query = input(...)
    messages.append({'role': 'user', 'content': query})
    llm_context = LLMCallHookContext(llm=llm, agent=agent, session_id=session_id, messages=messages)
    trigger_hook("before_turn_call", llm_context)      # ① 注入相关记忆
    agent.agent_loop(messages=messages)                # ② 正常对话（LLM + 工具）
    if not trigger_hook("after_turn_call", llm_context):  # ③ 保存会话 + 抽取记忆
        break
```

system prompt（新会话）也拼入记忆目录，与 skills 并列：

```python
'content': (
    f'你是一个编程助手，堪比 Claude Code！你的工作目录在 {WORKDIR} 下\n'
    f'{build_system_prompt_for_skills()}\n'
    f'{build_memory_system_prompt()}'
)
```

### 2.4 运行闭环

```
启动：scan_skills + recovery；新会话时 system = 助手设定 + skills 目录 + 记忆目录/引导
每轮：
  before_turn_call → select_relevant_memories(近期对话) → load_memories → 注入 <relevant_memories>…</relevant_memories>
  agent_loop（LLM 带记忆作答）
  after_turn_call   → ① write_sessions 持久化 ② extract_memories(最近10条) → LLM 返回 JSON → write_memory_file 落盘 + 重建索引
跨会话：下次启动读 .memory/MEMORY.md → 记住偏好继续生效
```

抽取的 LLM 请求要求返回 JSON 数组 `[{name, type, description, body}]`，`memory.py` 用正则 `\[.*?\]` 抓取后解析；返回 `[]` 或解析失败都静默跳过，绝不因记忆失败影响主对话。合并（`consolidate_memories`）在文件数 ≥ 10 时可用，含"空结果保护"（LLM 返回 `[]` 不清库）。

## 3. 支撑变化：`hook.py` 事件与触发语义

1. **新增事件 `before_turn_call`**：语义上与既有 `after_turn_call` 对称——"Turn 之前"扩展位，ch10 用它注入记忆。
2. **`trigger_hook` 语义调整**：从"执行到首个返回非 None 即短路返回"改为"**执行全部回调，返回最后一个非 None 结果**"。原因是 `after_turn_call` 现在要挂**两个都必须执行**的回调（会话保存 + 记忆抽取），短路会让后注册的被跳过。

```python
# ch10/hook.py
def trigger_hook(event: str, *args):
    if event not in HOOKS:
        print(f"{event} 事件不存在"); return None
    result = None
    for callback in HOOKS[event]:
        r = callback(*args)
        if r is not None:
            result = r
    return result
```

对既有单回调站点（`before_tool_call` 权限放行/拦截、`after_turn_call` 会话）行为不变；这也顺带解决了 ch06 文档"注意点 1"标注的"短路 vs 拦截两种语义并存"的债。

3. **`main.py` 细节**：`session_id` 改回动态 `uuid.uuid4().hex[:8]`（此前 ch09 为测试硬编码过）；cprint 日志按事件细分（保存会话 / 注入记忆 / 抽取记忆）。

## 4. 设计收益

1. **长期记忆**：偏好/约束跨会话持续生效，Agent 不再每轮"失忆"——这是相对 ch09（只处理单会话内上下文）的新维度。
2. **全 hook 接入，零新机制**：记忆复用 `before_turn_call` / `after_turn_call` 事件 + `LLMCallHookContext`，没往 `tool.py` 塞工具，主循环只多了两行 trigger。
3. **按需注入 + 克制上下文**：每轮只注入"相关"记忆（LLM 挑相关、关键词兜底），不是把全部记忆塞给模型。
4. **静默失败设计**：抽取 / 合并 / 选择任一环节失败都返回空、不影响对话主流程，符合"记忆是增强而非必需"的定位。
5. **LLM 能力集中在"判断"**：选择、抽取、合并都交给 LLM，文件读写是薄薄一层，避免手写规则解析对话。
6. **落盘可审计**：`.memory/*.md` 明文可读，`MEMORY.md` 索引一目了然。

---

## 5. 注意点

1. **每轮两次额外 LLM 调用**：注入前的记忆筛选 + 结束后的抽取各一次（均静默兜底）。偏好抽取本可更懒，若在意延迟可把 `extract_memories` 改为只在轮次稀疏/有明确"记住"信号时触发。
2. **记忆包装随用户消息落盘**：`<relevant_memories>…` 拼接进 `messages[-1]` 后，`write_sessions` 会把带包装的 user 消息写进 `.sessions`——历史里会残留旧记忆文本（注入又按轮重算，属可接受；但与 ch09 压缩方向相反，真介意需改为注入后不持久化的临时消息）。
3. **记忆目录只在"新会话"进 system**：`build_memory_system_prompt()` 只在 `len(messages)==0` 时拼进 system（与 skills 同逻辑）；恢复的历史会话系统里无该片段，但每轮 `load_memories` 注入的正文仍生效。
4. **`select_relevant_memories` 的 LLM 选择走 `.memory` 的 name/description 目录**：相关度取决于 `description` 写得好不好；正则 `\[.*?\]` 假设 LLM 输出裸 JSON 数组，格式偏离即退化为关键词匹配。
5. **`trigger_hook` 语义变化是全文件性的**：ch10 起同一事件下的多个回调都会执行（返回取末值）。新增 `before_tool_call` 类"拦截"回调时须记得它是"末值放行"语义，多个拦截回调并存时需自行约定顺序/取反。
6. **`.memory` 已被 `.gitignore` 忽略**：记忆不会进版本库，换机器/克隆即空库，符合预期（若要团队共享需另行处理）。
