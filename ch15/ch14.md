# ch14 变更说明（对比 ch13）

> 一句话：ch14 的核心变化是引入 **后台任务机制**——新增 `background_task.py`，把耗时工具调用（`npm install` / `build` / `test` 等慢 bash 命令）丢进 **daemon 线程异步执行**，主循环立即拿到 `[Background task started with ID bg_0001]` 占位结果继续转；任务完成后自动以 `<task_notification>` 注入下一轮消息，让模型在同一条工作流里收到结果、接着干，而不是同步干等 120s。
> 接入改动极小：`tool.py` 给 bash 工具补 `run_in_background` 参数（工具数仍 13，不算新增工具）；`core/agent.py` 只在 `agent_loop` 接两处——工具分发分支加前后台决策、循环顶部拾取完成结果。**prompt.py / main.py / task.py / subagent / memory / error_recovery 均零改动**，subagent 的工具隔离不变。

## 2. 为什么需要后台任务：ch13 的工具调用是同步阻塞的

ch13 的工具分发是同步的：

```python
handler = TOOL_CALL_MAP[tool.name]
result = handler(**tool.tool_input)      # 同步执行，跑完才 append tool 消息
```

而 `run_bash` 内部是 `subprocess.run(..., timeout=120)`，几个真实场景会直接卡死主循环：

1. **慢命令阻塞主循环**：模型要 `npm install` / 构建 / 跑测试时，这一轮就停在 `subprocess.run` 上最长 120s——期间模型既不能继续规划、也不产生输出，体验像"死机"。
2. **长任务撞 120s 超时**：超过 120s 直接返回 `Timeout (120s)`，构建其实可能再等一会儿就成功——同步形态下白白失败。
3. **无法边跑边做**：真实 agent 遇到耗时命令应该"先开跑、继续做别的、完成后再汇报"，同步模型做不到。

真实 Claude Code 的 Bash 工具用 `background:true` 解决：命令放后台、立即返回"已在后台跑"，完成后由 harness 注入 `<task_notification>`。ch14 用最小机制把同一条语义补上：**慢命令启发式 + 显式 `run_in_background` 参数 + daemon 线程 + 完成通知**。

## 3. 核心变化

### 3.1 `background_task.py` —— 模块级后台状态 + 决策 / 派发 / 收集

模块级三件套 + 一把锁（worker 跑在 daemon 线程、主循环在别处读写，跨线程共享 dict 必须锁）：

```python
_bg_counter = 0
background_tasks: dict[str, dict] = {}   # bg_id → {tool_use_id, command, status}
background_results: dict[str, str] = {}   # bg_id → output
background_lock = threading.Lock()
```

**决策**：显式 `run_in_background` 优先，未表态才走慢命令启发式（启发式只认 bash、按命令关键字包含匹配 install/build/test/deploy…）：

```python
def should_run_background(tool_name, tool_input) -> bool:
    if "run_in_background" in tool_input:
        return bool(tool_input["run_in_background"])   # 显式 true/false 都是明确意图
    return is_slow_operation(tool_name, tool_input)    # 未表态才"猜"慢命令
```

**派发**：先在锁内登记 `running`（让主循环立刻可见），再启动 daemon 线程；worker 复用 `TOOL_CALL_MAP` 的**同步 handler**（前后台同一套执行逻辑），完成后再锁内置 `completed` 并把结果写进 `background_results`。worker 套 `try/except`——后台异常也写回并置 `completed`，不留永久 `running` 的僵尸任务。

```python
def start_background_task(block) -> str:               # block 是本仓库 ToolCall
    global _bg_counter
    _bg_counter += 1
    bg_id = f"bg_{_bg_counter:04d}"
    cmd = block.tool_input.get("command", block.name)
    def worker():
        try:
            result = execute_tool(block)               # TOOL_CALL_MAP[block.name](**剥离后的参数)
        except Exception as e:
            result = f"Error in background task: {type(e).__name__}: {e}"
        with background_lock:
            background_tasks[bg_id]["status"] = "completed"
            background_results[bg_id] = result
    with background_lock:
        background_tasks[bg_id] = {"tool_use_id": block.tool_id,
                                   "command": cmd, "status": "running"}
    threading.Thread(target=worker, daemon=True).start()
    cprint(f"[background] dispatched {bg_id}: {cmd[:40]}", color="yellow")
    return bg_id
```

**收集**：锁内把 `completed` 的 pop 出来（通知过一次即移除，防重复喂给模型），拼成 `<task_notification>`（摘要截前 200 字，完整输出仍留在 `background_results`），返回给主循环注入：

```python
def collect_background_results() -> list[str]:
    ...
    # "<task_notification>\n  <task_id>bg_0001</task_id>\n  <status>completed</status>\n
    #   <command>npm install</command>\n  <summary>...前200字...</summary>\n</task_notification>"
```

**适配说明**（上游参考版 → 本仓库分层）：
- 上游 `from tools import TOOL_CALL_MAP` → 本仓库 `TOOL_CALL_MAP` 在 `tool.py`，改 `from tool import TOOL_CALL_MAP`；
- 上游遍历的工具块带 `.name/.input/.id` → 本仓库是 `tools/structed_tool.py` 的 `ToolCall`（`.name/.tool_input/.tool_id`），`execute_tool` / `start_background_task` 两处随之改名；
- 打印统一 `utils.color_print.cprint`（黄=派发、绿=完成），与 error_recovery / task 一致。

### 3.2 `core/agent.py` —— agent_loop 接两处

工具分发分支（在权限 hook、`compact` 特判之后）：

```python
# ch14: 慢命令或显式 run_in_background 转后台执行，立即回占位结果让主循环继续转
if should_run_background(tool.name, tool.tool_input):
    bg_id = start_background_task(tool)
    result = (f"[Background task started with ID {bg_id}] "
              f"command is running in the background; "
              f"you will be notified via <task_notification> "
              f"when it completes.")
else:
    # run_in_background 只是决策字段，不传给底层 handler（run_bash 不接收该 kwarg）
    kwargs = {k: v for k, v in tool.tool_input.items() if k != "run_in_background"}
    result = TOOL_CALL_MAP[tool.name](**kwargs)
```

- **被后台的工具调用同样会收到一条 `role="tool"` 占位结果**（`tool_call_id` 对齐）：保证 assistant 消息里的每个 `tool_calls` 都有对应 tool 响应，API 不会因"悬空 tool_calls"报错；模型也立刻知道"已转后台、会通知我"。

每轮 `while` 循环顶部拾取已完成的后台任务并注入：

```python
for note in collect_background_results():
    if messages and messages[-1].get("role") == "user":
        messages[-1]["content"] = f"{messages[-1]['content']}\n\n{note}"   # 就近合并
    else:
        messages.append({"role": "user", "content": note})                 # 否则追加一条
```

- 末尾正是 user 消息（新问题的首轮，含 `before_turn_call` 注记忆的场景）就**就近合并**，避免连排两条 user 消息——与 main.py 里记忆注入是同一个手法；否则追加一条 user 消息让模型看到结果。
- 模型无需轮询：后台一旦完成，下一轮顶部自动注入；同一轮内多步工作流会自然接上（派发 → 模型继续做别的 → 结果到达 → 模型收尾）。

### 3.3 `tool.py` —— bash 工具 schema 补 `run_in_background`

工具总数不变（仍 13，不是新增工具），只是给 bash 的 `args_schema` 加一个可选 boolean：

```python
StructuredTool(
    name="bash",
    description="Run a shell command.",
    args_schema={
        "type": "object",
        "properties": {
            "command": {"type": "string", "description": "The shell command to run."},
            # s13: 对齐真实 Claude Code —— 模型可显式声明后台执行，should_run_background 据此命中
            "run_in_background": {"type": "boolean",
                                  "description": "Run in the background, return immediately."},
        },
        "required": ["command"],
    },
    func=run_bash,
),
```

- **为什么加这个字段**：启发式只该兜底"模型没表态"——某次 `npm install` 模型想同步等结果（显式 `false`）、或某条快命令想后台（显式 `true`），都必须有表达通道。不加字段，模型根本没机会发 `run_in_background`，显式优先逻辑就永远走不到。
- **prompt.py / main.py 零改动**：bash 的 description 不变、工具名列表不变；新参数随 requests 的 `tools` schema 直接上送，模型据此知道可选传 `run_in_background`。
- **`run_in_background` 只是决策字段**：前台调用与后台 `execute_tool` 都会把它从 kwargs 里剥离，不传给 `run_bash`（其签名只有 `command`，硬传会 `TypeError`）。

## 4. 设计收益

1. **主循环不被慢命令卡死**：耗时命令占位即回（毫秒级），模型可在同一轮继续规划 / 并行发其他工具，而不是在 `subprocess.run` 上干等。
2. **前后台共用同一 handler**：后台线程跑的就是 `TOOL_CALL_MAP` 的同步入口，行为一致，不会出现前台/后台两套执行逻辑分叉。
3. **完成自动通知、防重复**：`collect_background_results` 锁内 `pop`（通知一次即移除）+ 200 字摘要注入下一轮，模型不用主动轮询；完整输出仍存 `background_results` 供后续扩展。
4. **显式优先 + 启发式兜底**：模型的意图可表达（`run_in_background: true/false`），又不强制它每次记得声明——慢命令没表态也能被"猜"到。
5. **改动面小、零侵入既有机制**：新增 1 文件 + 改 2 文件的接线点；task / subagent / memory / error_recovery / prompt / main 一行没动，`SUB_TOOLS` 依旧隔离（后台机制不泄漏给子代理）。

---

## 5. 注意点

1. **只对 bash 模拟慢命令**：`is_slow_operation` 仅认 bash；非 bash 工具只有显式 `run_in_background` 才可能后台，但 schema 里没这字段、模型不会发，实际只影响 bash。
2. **后台仍复用 `run_bash` 的 120s 超时**：超过 120s 的构建在后台也会返回 `Timeout (120s)`。教学取舍——没有给后台单独放开超时，需要时可在 base_tools 给 `run_bash` 加可选超时参数。
3. **后台状态是进程内存、不落盘**：`background_tasks / background_results` 是模块级 dict，进程退出（daemon 线程随之中止）任务即丢失、重启无残留——与 task.py 的 `.tasks/*.json` 落盘机制不同。
4. **通知注入时机 = 下一轮循环顶部**：若模型派发后台后立刻 `finish_reason=='stop'` 结束本轮，结果要等用户下一条消息触发新的 `agent_loop` 才会注入；同一轮内的多步工作流则会自然接上。
5. **摘要只截前 200 字**：长输出不会全文塞进上下文（完整结果留在 `background_results`）；当前没有"按需再查完整输出"的工具，可留作后续扩展。
6. **`run_in_background` 已剥离再执行**：无论前后台，底层 handler 拿到的 kwargs 都不会含该字段；它只在 `should_run_background` 决策期有意义。
