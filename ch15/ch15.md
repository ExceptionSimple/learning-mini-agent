# ch15 变更说明（对比 ch14）

> 一句话：ch15 的核心变化是引入 **cron 定时任务调度器**——新增 `scheduler.py`，让模型能预约一条 5 段 cron 表达式（"每天早上 9 点巡检""每 5 分钟同步一次"），后台 daemon 线程每秒轮询、到点入队。**参考 s15 的处理过程**：scheduler 是纯调度库（只负责"到点入队"，不驱动 agent）；"空闲时把到点任务投递成一轮新回合"的职责放在 `main.py`——新增 `queue_processor_loop` daemon 线程，用 `agent_lock` 与用户回合串行化、绝不打断正在进行的对话；投递的 cron 回合其整条 stdout 重定向进 `scheduler.log`，用户回合输出不受影响。
> 接入改动：`scheduler.py` 新增（纯 stdlib、自包含）；`tool.py` 追加 3 个 cron 工具（工具 13→16）；`main.py` 重构出 `run_turn` / `run_turn_logged` / `queue_processor_loop`。**`core/agent.py` / `background_task.py` 与 ch14 逐字节一致**——cron 不进 `agent_loop`，ch14 的后台任务机制原样保留。

## 2. 为什么需要定时任务：background_task 解决不了"到点跑"

ch14 的 `background_task` 语义是**"现在跑、跑完通知"**（立即执行 + `<task_notification>`）；真实 agent 还有另一类诉求——**"现在不跑、到点才跑"**：

1. **轮询任务不该占回合**：每 5 分钟看一眼某状态、每天固定时刻巡检——这些事不该由用户逐条驱动，也不该用后台任务"现在跑一轮然后 sleep"那样把线程挂死。
2. **非阻塞调度**：scheduler 必须与 agent 主循环解耦——调度线程独立轮询，绝不能在 `agent_loop` 里同步 `sleep` 等到点。
3. **到点后如何进入对话**：这是与 ch14 最大的不同。cron 到点并不立刻有"用户问题"，它要把一条系统生成的 prompt 交给模型执行。参考 s15 的答案：**先入队，等 agent 空闲时投递成一轮新回合**——用户正在对话时绝不半路插话。

所以本仓库把 cron 拆成两层：
- `scheduler.py`（库层）**只调度、只入队**：daemon 线程到点把 job 塞进 `cron_queue`，不碰 `messages`、不驱动 agent。
- `main.py`（应用层）**消费并驱动**：`queue_processor_loop` 检测到队列非空且 agent 空闲（`agent_lock` 空闲）时，取走任务、拼成一条 user 消息投递一轮完整回合。

> 一条粗比对：background_task = "async 一次"；scheduler = "async 定时"；而"定时结果如何回到模型面前"正是 ch15 相对上游参考实现重新适配的点。

## 3. 核心变化

### 3.1 `scheduler.py` —— 纯 stdlib 自包含调度器（参考实现，几乎原样接入）

`CronJob` 与模块级状态：

```python
@dataclass
class CronJob:
    id: str
    cron: str        # "0 9 * * *"：分 时 日 月 周
    prompt: str      # 触发时要注入给模型的消息
    recurring: bool  # True = 周期重复；False = 一次性（触发后自动删除）
    durable: bool    # True = 落盘持久化（重启后恢复）

scheduled_jobs: dict[str, CronJob] = {}   # job_id → job
cron_queue: list[CronJob] = []            # 已到点、待消费的 job
cron_lock = threading.Lock()              # 保护 scheduled_jobs / cron_queue
agent_lock = threading.Lock()             # 预留：main 侧用它与用户回合串行化（见 3.3）
_last_fired: dict[str, str] = {}          # job_id → "YYYY-MM-DD HH:MM"，防同分钟重复触发
```

- **匹配语义**：`cron_matches` 按标准 cron——分/时/月必须全中；**日与周两者都受限时取 OR**（满足其一即可），避免"每月 1 号 且 周一"这类双重限定导致永不再触发。
- **校验**：`validate_cron` 入口拦截非法表达式（5 段、逐字段范围：分 0-59 / 时 0-23 / 日 1-31 / 月 1-12 / 周 0-6，支持 `*` `*/n` `,` `-`）。
- **daemon 调度循环**（模块级 `import scheduler` 即启动，无需手动拉线程）：

```python
def cron_scheduler_loop():
    while True:
        time.sleep(1)
        now = datetime.now()
        minute_marker = now.strftime("%Y-%m-%d %H:%M")  # 带日期，跨天不误判
        with cron_lock:
            for job in list(scheduled_jobs.values()):
                if cron_matches(job.cron, now):
                    if _last_fired.get(job.id) != minute_marker:
                        cron_queue.append(job)                     # 只入队，不驱动 agent
                        _last_fired[job.id] = minute_marker
                    if not job.recurring:
                        scheduled_jobs.pop(job.id, None)           # 一次性：触发即删
```

- **durable 落盘**：注册 / 取消时若 `durable` 为真，同步写 `.scheduled_tasks.json`；启动时 `load_durable_jobs()` 恢复（坏条目跳过告警）。一次性（session-only）任务不落盘——重启后本就该消失。
- **队列访问**：`has_cron_queue()` 查询是否有待投递任务，`consume_cron_queue()` **取走即清空**（同一批触发只投递一次）。
- **日志落盘**：`cron_log(msg)` 把 register / fire / cancel / error / 线程启停统一写入当前目录 `scheduler.log`（带时间戳、无 ANSI），**不再 print 到终端**——避免骑在悬空的 `[USER] > ` 提示符上污染界面（ch15 体验修复，见 §5.5）。

### 3.3 `main.py` —— 参考 s15 的重构：空闲投递线程 + 回合串行化

ch14 的主循环是一个直接 `while True: input() → agent_loop` 的 REPL。要让 cron 到点任务**不用等用户下一句输入**就能进对话、又**不打断进行中的回合**，ch15 把回合抽成可复用的 `run_turn`，并新增一个后台投递线程：

**把"一轮对话"抽成 `run_turn(query)`**（用户回合与 cron 投递共用同一条驱动路径）：

```python
def run_turn(query: str) -> bool:
    messages.append({'role': 'user', 'content': query})
    llm_context = LLMCallHookContext(...)
    trigger_hook("before_turn_call", llm_context)      # 注入相关记忆
    agent.agent_loop(messages=messages)
    return trigger_hook("after_turn_call", llm_context)  # 保存会话 + 抽取记忆
```

**空闲投递线程 `queue_processor_loop`**（daemon，`main()` 内启动）：

```python
while True:
    time.sleep(0.2)
    if not has_cron_queue():
        continue
    if not agent_lock.acquire(blocking=False):   # 拿不到锁 = 用户回合正在跑 → 跳过
        continue
    try:
        if not has_cron_queue():                 # 双检：等锁期间可能已被消费光
            continue
        fired = consume_cron_queue()
        run_turn_logged("\n".join(f"[cron] {j.prompt}" for j in fired))
    finally:
        agent_lock.release()
```

**为什么 `agent_lock` 非阻塞抢占**：锁被用户回合持有说明正在对话——跳过本轮等下一个 0.2s，**绝不打断**；主循环同样用 `with agent_lock:` 包住用户回合，两条来源串行执行、互不覆盖。

**主 REPL 只改两处**：`query` 空输入（裸回车）`continue` 不触发回合；否则 `with agent_lock: run_turn(query)`。

**cron 回合输出重定向 `run_turn_logged`**：用户回合输出照常上终端，而投递线程的整条链路（钩子打印、agent_loop 流式思考/回答、`[tool]` 行、记忆抽取）经 `contextlib.redirect_stdout` 全部写入 `scheduler.log`——因为投递在 `agent_lock` 下独占运行（主线程此时阻塞在 `input()`/锁上不打印），重定向只会捕获本回合，不会吞掉用户回合。

```python
def run_turn_logged(query: str) -> bool:
    with open(LOG_PATH, "a", encoding="utf-8") as f, \
            contextlib.redirect_stdout(f):
        f.write("\n--- cron turn ---\n")
        return run_turn(query)
```

**`core/agent.py` 对 cron 零改动**：ch14 加的后台任务拾取（每轮顶部 `collect_background_results`）原样保留；cron 的入队 → 消费 → 投递全部发生在调度线程 / main 的空闲投递线程，不塞进 `agent_loop`。

## 4. 设计收益

1. **模型能预约"到点做的事"**：`schedule_cron` 注册后由 daemon 线程接管，agent 不必自旋 sleep，也不会在长回合里被某次轮询卡住。
2. **到点自动投递、不用等用户输入**：`queue_processor_loop` 在 agent 空闲时把 fired 任务当一轮新回合喂给模型（`[cron] {prompt}`），多任务同一分钟触发则合并成一条。
3. **绝不打断进行中的对话**：`agent_lock` 非阻塞抢占 + 双检——用户回合运行时 cron 只排队，空闲后才补投；两条来源共享 `run_turn` 单一路径，行为一致。
4. **调度与驱动解耦、改动面小**：scheduler 是纯 stdlib 库（不 import 任何 agent 代码），工具仅 +3 个走通用分发，`core/agent.py` / prompt 零改动；参考实现几乎原样接入，只把"何时驱动"适配到本仓库 REPL 形态。
5. **终端不被 cron 刷屏**：register/fire/投递详情与整轮 cron 回合输出都进 `scheduler.log`，用户界面只保留用户回合的输出与一条极简"cron turn done"提示。

## 5. 注意点

1. **cron 只在进程内生效，durable 才跨重启**：daemon 线程随进程退出中止；仅 `durable=True` 的任务落盘 `.scheduled_tasks.json`，重启后自动恢复（session-only 任务重启即丢，与 background_task 的进程内存状态一致）。
2. **一次性 vs 循环**：`recurring=False` 的任务触发一次后立即从 `scheduled_jobs` 移除（并同步落盘）；`* * * * *` 这类循环任务每分钟触发一次，由 `_last_fired` 按分钟去重。
3. **日/周双受限取 OR**：`cron_matches` 按 cron 经典规则，`dom` 与 `dow` 都受限时满足其一即命中——写"每周一 且 每月 1 号"之类的表达式可能不是你想的语义。
4. **`scheduler.py` 内部两处注释为参考实现原样（未随 s15 适配更新）**：`consume_cron_queue` docstring 仍写"agent_loop 每轮顶部调用"、`agent_lock` 注释仍写"预留（当前未用）"——在本仓库实际由 main 的空闲投递线程消费、由 main 使用该锁。为保持参考库逐字可对比，这两处注释未改动，读代码时以实际接线为准。
5. **体验修复（s15 复盘）**：cron 异步输出初版会骑在悬空的 `[USER] > ` 提示符上，且裸回车会触发空回合空转——ch15 用 **cron 日志落盘 `scheduler.log` + cron 回合 stdout 重定向** + **空输入过滤** 三者收敛：终端干净、`tail -f scheduler.log` 可查 cron 全链路（含到点回合的思考/回答/工具输出）。
6. **投递的 cron 回合会真实消耗一轮 LLM**：每次到点触发就是一轮完整对话（含记忆抽取落盘），频率过高（如 `* * * * *`）会持续产生请求与 token 成本——教学示例够用，真实场景建议抬高频率或加节流。
7. **投递失败不杀线程**：`run_turn_logged` 抛错时 `queue_processor_loop` 捕获、终端打红一次告警，后续 cron 仍能正常投递。
